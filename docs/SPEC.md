# OrderApp 仕様書(引き継ぎ用)

学園祭(生駒祭)の飲食出店向け注文管理システム。複数の出店(=インスタンス)を1つのアプリで運用し、注文受付・厨房表示・履歴・売上統計・CSV出力を行う。

> このリポジトリは **Public** です。パスワード・APIキー・個人のメールアドレスなどの秘密情報は、コードにもこのドキュメントにも書かないこと(環境変数名のみ記載)。

最終更新: 2026-10-22

---

## 1. 概要

| 項目 | 内容 |
|---|---|
| 目的 | 出店ごとの注文受付〜提供完了を端末上で管理し、売上を集計・CSV出力する |
| 利用者 | 出店スタッフ(Googleアカウントで招待された人)/ 全体管理者(Admin) |
| 利用端末 | スマホ・タブレット中心(モバイル前提のUI)。ライトテーマ固定 |
| 言語・時刻 | UIは日本語。時刻表示・日別/時間別集計はすべて **JST(Asia/Tokyo)** |
| 本番 | Vercel(GitHub連携で `main` へ push すると自動デプロイ) |

## 3. 用語

| 用語 | 意味 |
|---|---|
| インスタンス | 1つの出店(チーム)専用の空間。商品・注文・メンバー・編集履歴はインスタンスごとに独立 |
| Admin(全体管理者) | 全インスタンスを管理できるアカウント。`ADMIN_EMAIL`(常時管理者)+ `AdminInvite` テーブルで招待された人 |
| インスタンス管理者 | あるインスタンスの編集履歴を閲覧できるメンバー(`InstanceMember.isInstanceAdmin`) |
| メンバー | インスタンスに招待された Google アカウント(メールアドレスで照合) |
| トップ(トップ画面) | `/instances`。ログイン後に入るインスタンスを選ぶ画面(以前の呼び名「切替」「インスタンス選択」は使わない)。ヘッダーの「トップ」リンクと、Admin画面・シフト画面の「トップへ」から戻れる |

## 4. 権限モデル

| 操作 | 一般メンバー | インスタンス管理者 | Admin |
|---|:-:|:-:|:-:|
| 注文・厨房・履歴・商品・統計の利用(所属インスタンス内) | ○ | ○ | ○(所属していれば) |
| 編集履歴の閲覧 | × | ○(自インスタンスのみ) | ○(全インスタンス) |
| **編集履歴の取り消し**(注文・商品・シフトの変更を元に戻す) | × | ○(自インスタンスのみ。稼働中のみ) | ○(現在のインスタンス) |
| メンバー管理(`/members`: 自インスタンスへの招待、インスタンス管理者権限の付与・剥奪) | × | ○(自インスタンスのみ。稼働中のみ) | ○(全インスタンス) |
| **シフトの追加・編集・削除、役割の設定・並び替え・色、表のドラッグ変更**(`/shifts`) | × | ○(自インスタンスのみ。**停止中でも可**) | ○(全インスタンス) |
| シフトの閲覧(全員) | ○ | ○ | ○ |
| **決済リンク(PayPay / d払い)の登録・変更・削除**(`/payment`) | × | ○(自インスタンスのみ) | ○(現在のインスタンス) |
| **その他のQRの登録・ラベル/リンクの変更・削除**(`/payment`) | × | ○(自インスタンスのみ) | ○(現在のインスタンス) |
| 決済QR・その他のQRの閲覧・拡大(`/payment`) | ○ | ○ | ○ |
| `/admin`(インスタンス作成・削除・複製・停止、メンバー招待・権限変更、Admin招待) | × | × | ○ |

- インスタンス管理者の付与・剥奪・メンバー招待は、Admin が `/admin` から、またはそのインスタンスのインスタンス管理者が `/members` から行える。インスタンス管理者は **自分自身の権限は外せない**(ロックアウト防止)。
- メンバーの削除(1人ずつ・**一般メンバーの一括削除**とも)と表示名の変更は **Admin のみ**(インスタンス管理者は不可)。
- `ADMIN_EMAIL` のアカウントは `AdminInvite` の有無に関わらず常に Admin(最低1人は必ず管理者がいる状態を保つため)。
- **停止中(active=false)のインスタンスは、メンバーでも選択・操作できない**。**ただしシフトだけは例外**: 参加しているメンバーは閲覧でき、Admin と、そのインスタンスのインスタンス管理者(いずれもそのインスタンスのメンバーであること)はシフトと役割の追加・編集・削除もできる(注文・厨房・商品・メンバー管理などは従来どおりロック)。
- 判定ロジックは `src/lib/instance.ts`(`isAdminEmail` / `isInstanceAdmin` / **`canEditShifts`(シフト編集: Admin または そのインスタンスのインスタンス管理者。停止中でも可)** / `getCurrentInstance` ほか)。API は各ルートで同ファイルの関数を呼んで認可している。

### 5.1 共通UI

- ヘッダーは画面上部に固定(sticky)。ナビ(スライドするインジケーター付き): 注文 / 厨房 / 注文履歴 / 商品 / 統計。その横の別グループに トップ / シフト / メンバー・編集履歴(インスタンス管理者とAdminのみ)/ Admin(Adminのみ)。こちらは現在のページが反転表示されるだけでインジケーターは使わない(タブ数が増えて折り返し、表示が崩れるのを防ぐため)。インジケーターは折り返し時も位置・高さを個別に追従し、一致するタブがないページでは非表示。
- 右側: 自分のGoogleアイコン(押すと `/account`)、ログアウト(アイコンのみ)。アイコンがない/読み込めない場合は名前の頭文字の丸を表示(`components/Avatar.tsx`)。
- **「ページ上部へ戻る」ボタン**(`components/ScrollToTopButton.tsx`): 厨房と注文履歴が長くなったとき用。400px以上スクロールすると右下に丸い「↑」が出て、押すとスムーズに先頭へ戻る。
- モーダルは `fixed` + `z-30`(ヘッダー `z-20` より上)。
- **新しいバージョンのお知らせ**(`components/UpdateNotice.tsx`、`Providers.tsx` から全ページに表示): デプロイされた新しい版が出ると、画面下に「新しいバージョンがあります。再読み込みすると最新になります。」と **「再読み込み」「あとで」** の黒いバーを出す。**勝手には再読み込みしない。** 仕組み: ビルド時に `next.config.ts` が `NEXT_PUBLIC_APP_VERSION`(`VERCEL_GIT_COMMIT_SHA`、なければ `VERCEL_DEPLOYMENT_ID`、ローカルは `dev`)を埋め込み、`GET /api/version`(キャッシュなし)が今デプロイされている版を返す。開いているページが **60秒ごと・タブに戻ったとき** に見比べ、違えば通知する。「あとで」は10分間隠れ、まだ古ければ再表示。**注文画面(`/order`)と、ポップアップ(`fixed inset-0` の要素)が開いている間は出さない**(入力中の邪魔をしないため。閉じる/画面を移ると出る)。新しいモーダルも `fixed inset-0` で作れば自動で対象になる。
- **ブラウザ標準の `window.prompt` / `window.confirm` は使わない**(利用環境で動作しない)。確認は `ConfirmModal` またはアプリ内モーダルで行う。
- 画面端まで引っ張ったときにページ全体(ヘッダー含む)が伸びる Android のオーバースクロール効果と、プルダウン更新は `overscroll-behavior-y: none` で無効化している(`globals.css`)。
- **リンクカード(Discord / X 等)**: ルートレイアウトの `metadata` に Open Graph / Twitter Card を設定し、画像は `src/app/opengraph-image.png`(1200×630、ロゴ+「注文管理」)。URL をログイン前のページ(`/` → `/login`)にリダイレクトしても、クローラーは同じメタタグを読める。画像の絶対URLは `VERCEL_PROJECT_PRODUCTION_URL`(Vercel が自動設定する本番ドメイン)から組み立てる(`layout.tsx` の `metadataBase`)。**`/shifts` は専用のカード**(タイトル「シフトを確認」、画像 `src/app/shifts/opengraph-image.png` に「シフトを確認」の文字入り。`?instance=…` 付きも同じ)。リンクプレビューのクローラー(Discordbot / Twitterbot / Slackbot / facebookexternalhit / LinkedInBot / WhatsApp / TelegramBot / Applebot)は未ログインでログイン画面へ飛ばされるとそちらのタグを読んでしまうため、`/shifts` ではクローラーのUAだけ、個人データを含まない簡易ページ(タグ付き)を200で返す。普通のブラウザは従来どおり未ログインなら `/login` へ。他のページのカードは従来どおりルートの設定(画像 `src/app/opengraph-image.png`)。カードの見た目を変えるときは画像を作り直し、Discord 側は古い表示がキャッシュされることがある。
- 画像はドラッグ不可。**拡大縮小の禁止**(ピンチ・ダブルタップ・Ctrl/⌘+ホイール・Ctrl/⌘ と +/-/0 のキー: `viewport` の `maximumScale=1`・`userScalable=false`、`globals.css` の `touch-action: pan-x pan-y`、`Providers.tsx` で iOS Safari の `gesture*` と2本指の `touchmove` を打ち消す)と、**右クリック・長押しのメニューの禁止**(`contextmenu` をページ全体で抑止。入力欄でも出ない。`globals.css` の `-webkit-touch-callout` も併用)。ブラウザ本体のメニューからの拡大縮小や、一部ブラウザ・OSのアクセシビリティ設定による拡大は、ページ側では止められない。テキスト選択は入力欄以外で無効。

### 5.1.1 アプリとしてのインストール(PWA)

- `src/app/manifest.ts` が Web App Manifest(`/manifest.webmanifest`)を配信する。`display: standalone`、`theme_color: #171717`、アイコンは `public/icons/` の PNG(192 / 512 / maskable 512)。iOS 用は `src/app/apple-icon.png`。
- これがないと Android Chrome は「ショートカット」しか作れず、起動時に Chrome の操作バー(Chromeで開く等)が出る。マニフェストがあるとインストールが通常のアプリ(WebAPK)になり、バーなしで全画面表示される。
- アイコンは `public/logo.svg` から `rsvg-convert` で生成した(maskable は背景を全面ダークにし、ロゴを中央約62%に縮小)。ロゴ変更時は同様に再生成すること。
- 注意: WebAPK の作成には端末側で Google Play 開発者サービスが必要。メーカー製タブレットなどで利用できない場合、マニフェストがあっても Chrome が従来のショートカットにフォールバックし、バーが残ることがある。

### 5.2 注文の状態

`WAITING`(待機中) → `COMPLETED`(提供済み)/ `CANCELLED`(キャンセル)

- 注文確定時は `WAITING`。「提供完了」で `COMPLETED`(完了時刻を記録。完了時に支払い方法を変更可能)。
- 「キャンセル」は厨房画面から。キャンセル済みの注文は **売上・CSV出力・統計に含まれない**。
- 注文の編集(商品・数量・客の特徴・支払い方法)は厨房・履歴の両方から可能。

### 5.3 支払い方法

`CASH`(現金/金券)/ `PAYPAY`(PayPay)/ `D_PAYMENT`(d払い)。定義は `src/lib/payment.ts`。

このほかに **`UNKNOWN`(不明)** がある。注文時・提供完了時には選べず、**履歴の「編集」から、提供済みの注文にだけ**選べる(あとから支払い方法が分からなくなった注文用。編集履歴に「支払い方法: A → 不明」と残り、取り消せる)。API(`PATCH /api/orders/[id]`)も、提供済み以外の注文を「不明」に変えるのは拒否する(すでに不明の注文を他の項目の編集で不明のまま保つのは可)。不明の注文は、CSV出力では「不明」、統計では売上に含まれ決済手段別に「不明」の行(灰色)が出る(不明の注文が1件も無いうちは出ない)。不明の注文を差し戻して厨房で提供完了にするときは、支払い方法を選び直す必要がある(選ぶまで確定できない)。

### 5.4 商品

- 価格は円の整数、**0円も可**(検品・廃棄など売上に載せない記録用)。
- **削除は論理削除**(`active=false`)。過去の注文・CSVは影響を受けない。
- **削除時は確認のため商品名の入力が必要**(インスタンス削除も同様)。
- 画像: アップロード(png/jpeg/webp/gif、5MB以下 → Vercel Blob)または**デフォルト画像ギャラリー**から選択。`/public/defaults/products/` の SVG を `src/lib/defaultProductImages.ts` に登録する方式(料理/串物/スナック/スイーツ/飲み物/その他/廃棄/検食)。
- 画像URLは「`/defaults/products/` 配下」または「Vercel Blob の公開URL」のみ許可(`isValidProductImagePath`)。外部URLは不可。
- AIによる画像生成は検討の末 **見送り**(実装しない方針)。

### 5.4.1 決済QR(`/payment`)

ヘッダーの「決済」から開く、インスタンスごとの PayPay / d払い の決済リンクのQR表示画面。

- **全メンバーが閲覧可**。QRをタップすると画面いっぱいに拡大(どこかをタップで閉じる)。未登録の方式は「まだ登録されていません」と表示。
- **登録・変更・削除は Admin とそのインスタンスのインスタンス管理者のみ**(同画面の入力欄。一般メンバーには入力欄が出ない)。API でも同じ判定。
- 入力できるのは `https://` で始まるリンク(500文字以内)のみ。QRはサーバー側で `qrcode` により生成した画像で、ブラウザ側にQRライブラリは持たない。誤り訂正レベルは最強の H で、中央に「サービスの頭文字(PayPay=P、d払い=d)」をゴシック体(サンセリフ)で入れたバッジ(QR面積の約4%)を重ね、方式ごとに色(PayPay=赤、d払い=橙。バッジの枠と文字・カード上端・見出し)も変えて見分けられるようにしている。**PayPay・d払いのロゴは商標のため使わず、頭文字は文字のみ**。
- **QRから登録**: 入力欄の下の「カメラでQRを読み取る」(端末のカメラ。HTTPS・カメラ許可が必要)/「QR画像から読み取る」(保存済みの画像・スクリーンショット)で、決済リンクのQRを読み取って入力欄に入れられる。**読み取っただけでは保存せず**、内容を確認して「登録」を押して確定する。`https://` で始まらないQRは入力欄に入れずエラー表示。読み取りはブラウザ内(`jsqr`、読み取り開始時に遅延読み込み。`src/lib/qrScan.ts`)で完結し、画像やカメラ映像はサーバーに送らない。
- 登録・変更・削除は編集履歴(種別「設定」)に記録する(リンクそのものは履歴に残さない)。インスタンスを複製してもリンクは引き継がない。

#### その他のQR(`/payment` の下部)

PayPay / d払い のほかに、**アンケート・連絡先・店のページなど任意のQR**を、インスタンスごとに最大20件まで登録して表示できる(`OtherQr`)。表示(拡大含む)は全メンバー、登録・変更・削除は決済リンクと同じ Admin とそのインスタンスのインスタンス管理者のみ。

- **登録の流れ**: 「QRを追加」カードで ①リンク(`https://`)を入力するか、カメラ/画像でQRを読み取る → ②**ラベルがサイトのメタデータから自動で入る**(入力が止まって約0.6秒後、または読み取り直後に取得) → ③ラベルは**登録の前に自由に直せる** → ④「登録」を押して確定。読み取り・自動入力だけでは保存しない。
- **ラベルの自動入力**: サーバーが `GET /api/other-qrs/metadata?url=…` でそのページを取得し、`og:title` → `twitter:title` → `<title>` → `og:site_name` の順に採用(40文字まで)。取れなければドメイン名を入れ、「サイトのタイトルを取得できなかった」と表示する。**手で入力したラベルは自動入力で上書きしない**。「サイトから取得」ボタンを押したときだけ、手入力も含めて入れ直す。
- **後から変更**: 登録済みの各カードで、ラベルとリンクの両方を変更して「変更を保存」、または「削除」(確認あり)。**既存QRのリンクを変えてもラベルは自動では変わらない**(「サイトから取得」で入れ直せる)。
- **ラベル取得の安全策(SSRF対策)**: 取得先は `https://` のみ・標準ポート(443)のみ・ユーザー名/パスワード付きは不可。**内部・私設アドレス(127.*、10.*、192.168.*、169.254.*、IPv6のローカル等)は接続の瞬間に確認して拒否**し、リダイレクトは3回まで(毎回同じ検査)。本文は256KBまで、5秒でタイムアウト。取得できるのは権限のある人だけ。文字コードはヘッダーと `<meta charset>` に従う(Shift_JIS/EUC-JPも文字化けしない)。`src/lib/pageMeta.ts`。
- QRの見た目は決済QRと同じ(サーバー側で生成、誤り訂正H、中央にラベルの頭文字)。色は共通の黒。
- 登録・変更・削除は編集履歴(種別「設定」)に記録(ラベルは載せ、リンクは載せない。取り消しはできない)。インスタンスを複製しても引き継がない。

### 5.4.2 アプリを開くQR(`/access-qr`)

トップ画面の「アプリを開くQRを表示」から開く、このアプリ自身のURLのQR表示画面。他の人のスマホで読み取ってもらい、アプリを開いてもらうために使う。

- ログイン済みなら誰でも開ける(インスタンスへの所属は不要)。QRをタップで拡大、「URLをコピー」「画像として保存」(PNG)ができる。
- QRの宛先は、Vercel の `VERCEL_PROJECT_PRODUCTION_URL`(本番ドメイン。リンクカードの基準URLと同じ)。無い環境(ローカル開発)ではアクセスしたホスト。
- 生成は決済QRと同じくサーバー側(`qrcode`、誤り訂正H)。中央にこのアプリのロゴ(QR幅の約22%)を重ねる。印刷用のA4データは別途ローカルで作成(リポジトリ外)。

### 5.5 注文明細のスナップショット

`OrderItem` は注文時点の **商品名・画像URL・単価** を自前で保持する(商品マスタの後日変更・削除があっても履歴/CSV/統計が変わらないようにするため)。注文を編集して商品を差し替えた場合は、その時点の商品情報で再スナップショットされる。

### 5.5.1 アカウント削除(`/account` の最下部)

誤操作が起きないよう、次の多重の安全策を入れている(`DeleteAccountSection.tsx` / `DELETE /api/account`)。

- ほかの設定から離した赤枠の専用セクションに置き、ボタンは確認画面を開くだけ(「アカウントを削除する…」)。
- 確認画面は、どのアカウントか(アイコン・名前・メール)と、**このアカウントについて実際に消えるもの**(参加インスタンス名、シフトの担当件数、通知の端末数など)と**消えないもの**を具体的に表示する。最初のフォーカスは「キャンセル」で、Enter / Space の押し間違いでは削除されない。Esc・背景のタップでも閉じる。
- 「完全に削除する」は、**自分のメールアドレスを正確に入力(大文字小文字は区別しない)** かつ **確認チェック** を入れるまで押せない。
- サーバーでも再確認する: ログイン中であること、**入力されたメールが自分のものと一致**すること、**Admin権限のあるアカウントは拒否**(Admin はメールで判定されており、アカウントを消しても権限が残って混乱するため。先にAdmin権限を外す)。
- 削除されるもの: `User`(Googleとの連携・セッション・通知端末も連鎖削除)と、そのメールの全 `InstanceMember`(シフトの担当も連鎖削除)。残るもの: 注文・商品などインスタンスの記録、編集履歴の「誰が操作したか」(`actorEmail`。監査用)。削除後は自動でログアウトし `/login` へ。同じGoogleアカウントで再ログインしても新規扱いで、インスタンスには再招待が必要。

## 6. 管理画面(`/admin`)

- **インスタンス**: 作成(名前・ラベル)、稼働/停止の切替、複製、削除。**復帰予約**: 停止中のインスタンスの行に「復帰予約」欄が出て、日時(日本時間)を指定して「予約する」と、その時刻を過ぎた最初の定期ジョブ(毎分)で自動的に稼働に戻る(誤差は1分程度)。予約中は日時と「予約を取り消す」を表示。手動で稼働に切り替えると予約は消える。稼働中のインスタンスには予約できない・過去の日時は不可。停止の予約(指定時刻に止める)は未実装。
  - ラベルはヘッダーに表示される短い名前(例: `vpro`)。空ならインスタンス名を表示。
  - **複製**: 有効な商品とメンバー(メールアドレスのみ)をコピー。注文履歴・編集履歴・インスタンス管理者フラグ・表示名はコピーしない。
  - **削除**: 商品・注文・メンバー・編集履歴を**すべて完全削除**(元に戻せない)。インスタンス名の入力による確認が必要。
- **メンバー**: インスタンスごとのアコーディオン(**初期は折りたたみ**)。
  - 招待: 展開したアコーディオンの**最上部**(メンバー一覧の上)に入力欄を置く。メールアドレスをカンマ・空白(混在可)区切りで複数同時に入力可(`src/lib/emails.ts`)。まだログインしていないアドレスも事前に招待できる。
  - 表示名: 優先順位は **管理者が設定した表示名(`InstanceMember.displayName`、インスタンスごと) → 本人が `/account` で設定した表示名(`User.displayName`) → Googleアカウント名(`User.name`、ログイン後) → メールアドレス**(`src/lib/memberName.ts` の `resolveName`)。名前クリックでインライン編集。名前の左にGoogleアイコンを表示。ログイン済みの人には「認証済み」バッジ。
  - Admin 一覧(常時管理者・招待された Admin)も同じ基準で名前を表示し、名前がある場合はメールアドレスを下に小さく併記する。Admin 自身の名前は、いずれかのインスタンスのメンバーに設定された表示名 → 本人設定の表示名 → Googleアカウント名 → メールアドレスの順。Admin 専用の名前欄は持たない。
  - 権限: 「一般 ⇔ インスタンス管理者」の切替。メンバー削除。
  - **管理者以外のメンバーを全員外す(Adminのみ)**: メンバー一覧の下の赤枠ボタンから、そのインスタンスの**Admin(全体管理者)とインスタンス管理者以外の全員**をまとめて外す(イベント終了後の片付けなど)。外れる人と残る人数を確認画面に表示し、**インスタンス名を正確に入力するまで実行できない**(サーバーでも一致を再確認)。外された人はそのインスタンスのメンバーでなくなり、シフトの担当も連鎖して外れる。アカウント自体・ほかのインスタンスへの参加・注文などの記録は消えず、再招待で戻せる(シフトの担当は戻らない)。一般メンバーがいないインスタンスにはボタンを出さない。編集履歴に「一般メンバーN人を一括で外しました」と記録する(`POST /api/admin/instances/[id]/members/remove-regular`)。
- **管理者(Admin)**: メールアドレスの複数同時招待、権限の削除。`ADMIN_EMAIL` の人は削除不可(常時管理者)。

### 6.1 シフトの入力(Admin)

- **役割の設定(Admin)**: 「役割の設定」で、登録・**色の変更**(丸いボタンから10色のパレット(`src/lib/shiftColors.ts`)または「自動」を選ぶ。色はリスト・シフト表・自分のシフト・PNGに反映。「自動」は名前から決まる従来の色(先頭8色)なので、何も選ばない役割の色は変わらない)・**名前の変更**(設定済みのシフトの役割テキストも一緒に更新。重複名は409)・**並び替え(上下ボタン=表示優先度)**・削除ができる(`PATCH /api/shifts/roles/[id]`、`POST /api/shifts/roles/reorder`。編集履歴に記録)。優先度が高い(上の)役割ほど、シフト表の行・フォームの選択肢・リスト内の担当の並びで先に出る。
- **役割は事前登録制**: 「役割の設定」でインスタンスごとに役割(20文字以内、重複不可)を登録し、シフトの担当行では登録済みの役割から選ぶ(`ShiftRole`)。役割を削除しても、設定済みのシフトの役割(文字列で保存)は変わらない。サーバーは未登録の役割を拒否する(編集時は、そのシフトがすでに使っている役割は許可)。
- **終了は開始の1時間後が既定**: 開始を入れると終了が自動で +1時間。終了を手で変える/調整ボタンを押すと、以降は開始を変えても終了は自動で動かない。
- **終了の調整ボタン**: 「+15分」「−15分」「+1時間」「−1時間」。同日内(00:00〜23:59)に収め、開始以前にはならない(下限は開始の1分後)。
- **同じ時間で追加**: 既存シフトの「同じ時間で追加」で、同じ日付・開始・終了時刻、担当と役割も写した状態で追加フォームが開く(日付はずらさない。必要なら日付だけ変えて保存する)(編集してから保存。保存するまで何も作られない)。

## 7. 編集履歴

`EditLog` に「誰が・いつ・何を」を人が読める文字列で記録(差分は `summary` に文章で保存)。インスタンス管理者・Admin のみ閲覧。

| 対象 | 操作 | 記録される内容 |
|---|---|---|
| 注文 | 新規登録 | 商品×数量 |
| 注文 | 編集 | 客の特徴・支払い方法・商品の変更前→変更後 |
| 注文 | キャンセル / 完了(個別・まとめて) | 完了時は支払い方法 |
| 商品 | 新規登録 / 編集 / 削除 | 商品名・価格(変更前→後)・画像変更 |
| メンバー | 招待(新規のみ) | 招待したメールアドレス |
| メンバー | 権限の切替 | 変更前→変更後の権限 |
| シフト | 追加 / 編集 / 削除 | 日付・時間帯・担当人数 |

### 7.1 履歴の取り消し(元に戻す)

注文・商品・シフトの変更は、編集履歴の「取り消す」で変更前の状態に戻せる。

- **仕組み**: 取り消せる履歴は、`EditLog.changes`(JSON)に、変更した対象ごとの「変更前の状態」「変更後の状態」(スナップショット)を持つ。取り消しは ①対象が今も「変更後の状態」のままか確認 → ②「変更前の状態」を書き戻す(`src/lib/revert.ts`)。
- **戻せる人**: 編集履歴を見られる人(そのインスタンスのインスタンス管理者・Admin)。稼働中のインスタンスの画面でのみ操作できる。
- **戻せる条件**: **その後に同じ対象が変更されていないこと**。あとから別の変更があると、後の変更を上書きしてしまうため取り消せない(409。新しい変更から順に取り消す)。条件を満たさない履歴にはボタンの代わりに案内文が出る。
- **取り消しも履歴に残る**(種別「取り消し」)。変更前後が入れ替わった形で保存されるので、取り消しをさらに取り消す(やり直し)ことができる。
- **対象ごとの動き**: 注文 = 状態(待機/完了/キャンセル)・支払い方法・客の特徴・明細を復元。新規登録の取り消しは注文の削除、削除の取り消しは元のIDで再作成。商品 = 名前・価格・画像・並び・有効を復元。**新規登録の取り消しは「無効化」**(商品は注文履歴が参照するため物理削除しない)。シフト = 時間帯と担当(人・役割)を復元。削除の取り消しは元のIDで再作成。担当のうち、すでにメンバーから外れた人の分は戻せない(件数を画面に表示)。時間が変わる復元では、通知・カレンダー登録の済み印もリセットする。ドラッグでの担当移動(シフトを分ける場合)は2つのシフトをまとめて戻す。
- **取り消せないもの**: この機能の追加前の履歴(`changes` が無い)、メンバーの招待・権限、決済リンク・その他のQR、シフトの役割(登録・名前・色・並び・削除)、アカウントやインスタンスの操作。
- 履歴1件あたり、JSONのスナップショットが追加で保存される(注文は明細を含む)。

記録されないもの: 表示名の変更、Admin の招待/削除、インスタンス自体の作成・複製・停止・削除、注文の物理削除。

## 8. データモデル(`prisma/schema.prisma`)

| モデル | 主な項目 | 備考 |
|---|---|---|
| `User` / `Account` / `Session` / `VerificationToken` | Auth.js 標準 | DBセッション。追加列: `displayName`(本人が設定する表示名)、`shiftReminder30`(30分前通知、既定 true) |
| `PushSubscription` | userId, endpoint(unique), p256dh, auth | 通知をオンにしたブラウザ/端末ごとの Web Push 購読情報。通知を切る・送信先が失効(404/410)したら削除 |
| `ShiftRole` | instanceId, name, sortOrder, color? | シフトで選べる役割の候補。`(instanceId, name)` が unique。インスタンス削除でカスケード削除 |
| `JobRun` | name(PK), ranAt, checked, sent | 外部cronの最終実行の記録(heartbeat)。`/admin` の「定期ジョブの状態(シフト通知・復帰予約)」に表示 |
| `Shift` | instanceId, startsAt, endsAt | 時間帯(UTC保存、表示はJST、分単位)。インスタンス削除でカスケード削除 |
| `ShiftAssignment` | shiftId, memberId, role, beforeNotifiedAt?, startNotifiedAt?, calendarAddedAt? | シフト×担当者×役割(役割は自由入力、20文字以内)。`*NotifiedAt` は通知送信済みの印で二重送信防止 |
| `AdminInvite` | email(unique) | Admin 追加用 |
| `Instance` | name, label, active, reactivateAt?, paypayUrl, dPaymentUrl, orderSound, createdAt | 削除すると配下をカスケード削除。`paypayUrl` / `dPaymentUrl` は決済リンク(空文字=未登録)。**複製しても引き継がない**(入金先が変わらないよう、複製先では登録し直す)。`orderSound` は厨房の追加音(`chime`/`bell`/`beep`/`none`、既定 `chime`)で、複製では引き継ぐ |
| `OtherQr` | instanceId, label, url, createdAt | 「その他のQR」(5.4.1)。`(instanceId, createdAt)` に index。インスタンス削除でカスケード削除。**複製では引き継がない** |
| `InstanceMember` | instanceId, email, userId?, isInstanceAdmin, displayName? | `(instanceId, email)` が unique。招待はメールで照合し、初回ログイン時に `userId` を紐付け(`src/auth.ts` の `signIn` イベント) |
| `Product` | name, price, imageUrl?, sortOrder, active | 論理削除 |
| `Order` | customerNote?, paymentMethod, status, createdAt, completedAt? | |
| `OrderItem` | productId?, productName, imageUrl?, unitPrice, quantity, servedQuantity | スナップショット保持。商品削除時 `productId` は null に。`servedQuantity` は待機中に先に渡した個数(0〜quantity、既定0) |
| `EditLog` | instanceId, entityType(ORDER/PRODUCT/MEMBER/SHIFT/INSTANCE), entityId, action(CREATE/EDIT/CANCEL/COMPLETE/DELETE/INVITE/REVERT), summary, actorEmail, changes?(取り消し用の変更前後スナップショット), createdAt | `(instanceId, createdAt)` に index |

マイグレーションは `prisma/migrations/`(init → 注文キャンセル+明細画像 → インスタンス管理者+編集履歴 → メンバー表示名 → ユーザー表示名 → シフトと Web Push → 役割マスタ → 役割の色 → 復帰予約 → カレンダー登録済み → 決済リンク → 履歴の取り消し用スナップショット → 厨房の注文追加音 → 一部提供の個数 → その他のQR → 支払い方法「不明」)。

## 9. CSV出力(`GET /api/orders/export`)

- 対象: ログイン中インスタンスの、**キャンセルを除く**全注文(古い順)。
- 文字コード UTF-8(BOM付き)、改行 CRLF。1行=注文明細1件。
- ヘッダー: `ID(OrderDB),timestamp,支払い方法,商品名,点数,商品単体価格,顧客特徴`(**顧客特徴は末尾**。注文の「客の特徴」を、その注文の全明細行に同じ値で入れる。未入力は空。既存の列の位置は変えていない)
- `timestamp` は `YYYY/MM/DD HH:mm:ss`(JST)。支払い方法は日本語ラベル。
- ファイル名: `売上管理簿_{インスタンス名}_{YYYY-MM-DD}.csv`

## 10. 売上統計(`src/lib/stats.ts`)

- 集計対象はCSVと同じ(キャンセル除外)。日付・時間帯はJSTで丸める。
- 日別: 売上金額 / 件数 / 売上個数。時間別: 選択した日の1時間ごとの売上金額(稼働時間帯を自動で切り出して表示)。
- 決済手段別: 注文の `paymentMethod` ごとに売上金額・件数・個数を合計し、全体に対する割合を横棒で表示(色は方式ごとに固定)。**支払い方法を分けて完了した注文は別の注文になっているため、分けた分も各手段に正しく入る**。「日別の内訳を表で見る」で日付×決済手段の売上表。
- 商品別: 注文明細の**商品名(注文時点の名前)**ごとに売上・個数を合計し、売上順(既定)/個数順で横棒ランキング表示。割合は売上の合計に対するもの。**単価0円の明細(廃棄・検食など)は集計から除く**(商品名が同じでも0円の行だけ除外)。商品に「種別」の項目は無いため、「種別」=商品ごと。
- **統計レポートのダウンロード**(`GET /api/stats/report?format=pdf|xlsx|csv&day=all|YYYY-MM-DD`、メンバー)。集計は画面と同じ(`getOrderStats`。`day` で1日に絞る)。形式ごとに専用のひな形:
  - **Excel**(`src/lib/statsXlsx.ts`、`exceljs`): シート「サマリー」(タイトル帯・対象・出力日時・総売上/件数/個数/客単価・決済手段別・商品の上位5)/「日別」(件数・個数・売上・1件あたり・決済手段別の売上、合計行、売上にデータバー)/「時間帯別」(時間×日付の売上、合計、濃淡ヒートマップ)/「決済手段別」(売上・割合・件数・個数・平均、日別の内訳)/「商品別」(売上順位・割合・個数・平均単価・注文数・日別の個数、データバー)。**合計・割合・平均は実際の数式**(値も保存しているので、数字を直すと再計算される)。A4・幅1ページに収まる印刷設定、ヘッダー行の繰り返し、フッターにページ番号と出力日時。
  - **PDF**(`src/lib/statsPdf.ts`、`pdf-lib` + `@pdf-lib/fontkit`): A4縦。タイトル帯、4つの数字(総売上・件数・個数・客単価)、決済手段別(棒+日別の表)、日別の売上(表+棒。2日以上のとき)、時間帯別(縦棒グラフ。全期間は全日の合計)、商品別(順位表+棒)。ページをまたぐ表は見出しを繰り返し、全ページにページ番号。データが無い節は「売上データがありません」。
  - **日本語フォント**: Noto Sans JP(SIL OFL)を `@expo-google-fonts/noto-sans-jp` から `node_modules` を読んで使い(リポジトリにフォントは置かない)、**PDFに使う文字だけに切り出して**(`subset-font`)埋め込む(pdf-lib 自身の部分埋め込みはこのフォントで文字が欠けるため。PDFは約0.3MB)。デプロイにフォントが含まれるよう `next.config.ts` の `outputFileTracingIncludes` に指定している。切り出しに無い文字が出たらサーバーログに警告。
  - **PDFの「日ごと」カード**(2日以上のとき。1日だけの対象では出ない): 該当の節の中に、1日=1枚のカードを**横3列**(各カードは本文幅の1/3)で並べ、行いっぱいになったら次の行へ折り返す。**決済手段別**の節=「日ごとの決済手段」(その日の売上と、手段ごとの売上+割合の棒)/**商品別**の節=「日ごとの売れ行き商品」(その日の**個数順の上位5品**。0円は除く)/**時間帯別**の節=「日ごとの時間帯別売上」(その日の時間別の縦棒。縦軸は全カード共通で日どうしを比べられる)。Excelには同じ内容が日別の列・表として既にあるため、カードはPDFのみ。
  - **日別CSV**(`src/lib/statsCsv.ts`): 1行=1日。列は 日付 / 注文数 / 点数 / 売上(円) / 売上:{決済手段}(円)(決済手段ごと。不明の注文があれば「不明」の列も) / 個数:{商品名}(商品ごと。0円の明細は除く)。売上のなかった日は出ず、その日の売れていない商品は0。UTF-8(BOM付き)・CRLF。対象を1日にするとその日の1行だけになる。ファイル名は `日別統計_{インスタンス名}_{全期間|日付}.csv`。
  - PDF/Excel のファイル名は `統計レポート_{インスタンス名}_{全期間|日付}.pdf/.xlsx`。時刻はJST。
- グラフは `src/components/BarChart.tsx`(HTML/CSS製の棒グラフ、ホバーでツールチップ、表表示切替)。

### 12.1 定期ジョブ(シフト通知・インスタンスの復帰予約)の仕組みと外部cronの設定

**同じ毎分の呼び出し1本**で、インスタンスの復帰予約(`Instance.reactivateAt` を過ぎた停止中のインスタンスを稼働に戻す)も処理する。復帰予約を使うには、cron-job.org のジョブが動いていること(`/admin` の「定期ジョブの状態」が正常)が前提。

- 通知は **Web Push**(ブラウザ標準、Service Worker `public/sw.js`)。アカウント設定で「通知をオンにする」→ ブラウザの許可 → 購読情報を `PushSubscription` に保存。
- 送信タイミングは `GET /api/cron/shift-notify` が決める: 開始の30分前〜開始(ユーザーが「30分前にも通知する」をオンにしている場合のみ)と、開始〜開始15分後(常に。それより遅れた分は送らない)。担当(`ShiftAssignment`)ごとに1回だけ。担当者がまだ一度もログインしていない(`userId` なし)場合は送らない。
- **Vercel Hobby の Cron は1日1回までなので使えない。** 外部の無料サービス **cron-job.org** から **毎分** 次を呼ぶ:
  - URL: `https://<本番ドメイン>/api/cron/shift-notify`、メソッド GET
  - ヘッダー: `Authorization: Bearer <CRON_SECRET と同じ値>`
  - 成功時は `{"checked":N,"sent":M}` を返す。設定不足は 401(合言葉違い)/ 503(VAPID 未設定)。
- **状態の確認**: `/admin` の「定期ジョブの状態(シフト通知・復帰予約)」に、cron の最終実行(何分前か)と直近の対象/送信件数が出る。「一度も実行されていません」「N分前(止まっている可能性)」なら、外部cron側(下の確認順②④)の問題。送信に失敗(一時的なエラー)した場合は、通知の窓が閉じるまで毎分再試行する。Web Push は `urgency: high` で送る。
- 通知が届かないときの確認順: ①アカウント設定が「この端末で通知オン」か(テスト通知で確認) ②cron-job.org の実行履歴が毎分成功しているか ③Vercel の環境変数 ④Vercel の Deployment Protection で `/api/cron/...` が弾かれていないか(弾かれると 401 の HTML が返る)。
- iPhone / iPad は iOS 16.4 以降で、**ホーム画面に追加したアプリ**として開いた場合のみ Web Push が使える。Android(Chrome)は通常のブラウザでも可。

## 13. 開発手順

```bash
# Node 22 系を使う(asdf の場合は .tool-versions に従う)
node -v            # v22.x であること
npm install        # postinstall で prisma generate が走る
npm run dev        # http://localhost:3000
npm run lint
npx tsc --noEmit
npm run build      # DB接続なしでも通る(Prismaクライアントは遅延初期化)
npm run db:seed    # サンプルインスタンス作成(ADMIN_EMAIL が必要)
```

- ローカルで画面を動かすには、`DATABASE_URL` が指すPostgresと、Google OAuth のクライアント(リダイレクトURIに `http://localhost:3000/api/auth/callback/google`)が必要。
- スキーマ変更時: `prisma/schema.prisma` を編集 → ローカルPostgresに対して `npx prisma migrate dev --name <名前>` でマイグレーションSQLを生成 → コミット。本番への適用はデプロイ時に自動。
- 認証が必要な画面の見た目確認は、認証を通さない一時的なプレビュー用ページ(`src/app/dev-preview-*`)にモックデータを渡して確認し、**確認後は必ず削除してからコミット**する運用にしていた。

## 14. デプロイ

- `main` への push で Vercel が自動ビルド・デプロイ。
- `vercel.json` の `buildCommand`: `prisma migrate deploy && next build`(マイグレーションはビルド時に自動適用)。`package.json` の `build` は `next build` のみ(ローカルビルドにDBを要求しないため)。
- 新しいマイグレーションを含む変更は、デプロイ時に本番DBへ自動適用される。**破壊的な変更は事前にバックアップ・影響確認を行うこと。**

## 15. 既知の制約・今後の課題

- **自動テストなし**(型チェック・lint・ビルド+手動確認で運用)。
- **依存パッケージの更新(2026-11-01)**: `npm audit` の重大(critical)・高(high)をすべて解消した(本番に載る依存は `npm audit --omit=dev` で 0件)。Next.js 16.3.0→16.4.3(`next` と `eslint-config-next` は正確なバージョンで固定)、Prisma 7.9.1→7.10.1(`prisma` / `@prisma/client` / `@prisma/adapter-pg` は**必ず同じバージョンにそろえる**)、`@vercel/blob` 経由の `zod` は `package.json` の `overrides` で 4.6.7 に固定。残る中程度(moderate)の警告16件はすべて ESLint 周りの開発用ツールで、本番には含まれない(`npm audit fix --force` は ESLint を古い版に戻す提案をするので**実行しない**)。更新のたびに `npm audit --omit=dev` と、型チェック・lint・ビルドを確認すること。
- 厨房画面は **ポーリング(2.5秒)** による更新で、WebSocket等のリアルタイム通信ではない。同時操作の競合(同じ注文を同時に編集等)は最後の書き込みが勝つ。
- 編集履歴は直近300件のみ表示。ページング・検索・絞り込みは未実装。
- **カレンダー追加は「ファイルの保存」まで**: 取り込んだかどうかはアプリから分からないため、ファイルを保存した時点で登録済みとして扱う。Googleカレンダーへの直接書き込み(OAuth・Google側の審査が必要)や、購読URLでの自動同期は未実装。シフトを別のシフトに分ける操作(表のドラッグで複数人のシフトから1人を動かす)ではUIDが変わるため、元のイベントが古い時間のまま残ることがある。
- 注文のAPI物理削除(`DELETE /api/orders/[id]`)はUIから使っておらず、履歴にも残らない。不要なら削除を検討。
- **メールアドレスの可視範囲**: シフト画面は、名前が未設定の人を `@` より前の先頭・末尾1文字以外を伏せて表示する(上記)。他人のメールアドレスが見えるのは Admin 画面とメンバー管理(`/members`)・編集履歴(`/edit-log`)のみで、いずれもインスタンス管理者・Admin 限定。一般メンバーが開く画面・APIには他人のメールアドレスは含まれない(自分のものは `/instances`・`/account` に表示)。新しい画面を足すときもこの前提を守ること。
- インスタンス管理者はメンバーの招待と権限の付与・剥奪ができるが、メンバーの削除・表示名変更はできない(Admin のみ)。
- 複製では表示名・インスタンス管理者の権限・シフトは引き継がれない。
- シフトは同日内(終了が開始より後)のみ。日をまたぐ場合は2つに分ける。シフトを編集すると、そのシフトの通知済みの印がリセットされ、まだ来ていない通知が再度送られる。
- 通知の精度は外部cron(毎分)に依存する。cron が止まると通知も止まる。
- 法的な整理(電気通信事業法など)は、本機能が自分たちのメンバー向けの業務連絡に限られる前提で問題ないと判断しているが、弁護士の確認を受けたものではない。
- Admin の招待/削除、インスタンスの作成・停止・削除は編集履歴に残らない。
- 画像はアップロード後に不要になっても Blob から自動削除されない。
